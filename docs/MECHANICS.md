# Механика работы

Здесь описано, как WinDiskMap получает данные и превращает их в дерево, счётчики и CSV.
Краткая версия для пользователя — в [README](../README.md).

## 1. Конвейер

```
Program.cs
  ├─ локальный путь
  │    └─ ScanRunner
  │         ├─ MftScanner      (администратор + локальный NTFS)
  │         └─ DirectoryWalk   (фолбэк: без прав, UNC, не-NTFS, --no-mft)
  │                │  IWalkSink / ScanIndex
  │                └─ BuildTree ──► TUI / CsvExporter
  │
  ├─ --agent-local ─► RemoteScanRunner ─► LocalAgentTransport ─┐
  └─ --remote host ─► RemoteScanRunner ─► PowerShellTransport ─┤
                                                              ▼
                                                     WinDiskMap.exe --agent
                                                     (тот же сканер, NDJSON в stdout)
                                                              │
                                                              ▼
                                          NdJson ──► TreeBuilder ──► TUI / CSV
```

Главное правило: **один индекс и один `TreeBuilder` на все режимы**. Агент не считает
агрегаты сам — он отдаёт плоские записи, хост строит дерево тем же кодом. Поэтому локальный,
агентный и удалённый скан дают одинаковые цифры.

## 2. Выбор режима сбора

| Условие | Режим |
|---|---|
| Есть права администратора, путь локальный, том NTFS, не задан `--no-mft` | `$MFT` |
| Всё остальное (включая UNC-шары и не-NTFS) | Обход каталогов |

MFT-ветка не «падает» вместе со сканом: если чтение тома или разбор записей не удался,
причина (тип, текст, `[stats: …]` / `[lookup: …]`) пишется в примечание сессии и в `--log`,
после чего скан продолжается обходом каталогов. В TUI это видно в шапке, в headless — в
итоговом отчёте.

## 3. Прямое чтение `$MFT` (`Core/Mft/MftScanner.cs`)

- Записи читаются с диска последовательно, без обхода каталогов: одна запись = один объект,
  логический размер берётся из атрибута `$DATA` (для резидентных данных — из заголовка).
- Если `$DATA` вынесен в extension-запись через `$ATTRIBUTE_LIST`, приоритет у **extension**;
  у split-атрибута берётся максимум по экстентам. FN-фолбэк используется только когда
  `$DATA` недоступен.
- Каждый атрибут `$FILE_NAME` — отдельный путь hardlink'а. Ссылки из extension-записей
  тоже считаются путями базовой записи; дедупликация — по паре `(родитель, имя)`.
  Если есть длинное имя, DOS-алиас 8.3 отбрасывается.
- Папки-репарсы (junction/symlink) остаются в дереве и видны с размером 0, но **не обходятся**
  и не попадают в счётчик папок. Это защита от петель (`Application Data` и т.п.).
- Признак reparse читается и из `$FILE_NAME`, и из `$STANDARD_INFORMATION`.
- Даты берутся из `$STANDARD_INFORMATION`, фолбэк — `$FILE_NAME`. Это реальные time-атрибуты
  файла, те же, что отдаёт Windows API. Приоритет `$FILE_NAME` проверяли и отвергли: он даёт
  расхождения с файловой системой.
- Выделенный размер (`On disk`) — сумма кластеров из data runs. Резидентные файлы кластеров
  не занимают и дают 0.
- Файл `$MFT` учитывается в размере корня тома: он реально занимает место и его нельзя
  получить обходом каталогов как обычный файл.
- Том с пустой меткой (нет корневого `$FILE_NAME`) обрабатывается отдельно.

## 4. Обход каталогов (`Core/DirectoryWalk.cs`, `Core/Win32Find.cs`)

- `FindFirstFileExW` с `FindExInfoBasic`: одно обращение даёт имя, атрибуты и размер;
  короткие имена 8.3 не запрашиваются.
- Несколько рабочих потоков параллельно обходят поддеревья и кладут записи в общий
  `IWalkSink`; мутирует индекс ровно один поток-сборщик. Поэтому результат не зависит от
  числа потоков (например, 1 и 8 потоков дают байт-в-байт одинаковый CSV).
- Для каждого файла `GetAllocated()` запрашивает `FILE_STANDARD_INFO.AllocationSize` — это
  сумма кластеров. Нюанс: для **резидентных** файлов Windows возвращает размер, округлённый
  до сектора (287 байт → 288), хотя кластеры не выделены. Такие файлы определяются через
  `FSCTL_GET_RETRIEVAL_POINTERS` с starting VCN = 0: `ERROR_HANDLE_EOF` (38) означает «экстентов
  нет», и в счёт идёт 0. Проверка делается только для `AllocationSize < 4096`, чтобы не
  тормозить обычные файлы.
- Если файл нельзя открыть, используется `GetCompressedFileSizeW`, а при ошибке — логический
  размер. Ошибка доступа не прерывает скан.
- Reparse-папки не обходятся, но остаются в дереве с нулевым размером (см. выше).
- Сетевые пути всегда идут обходом: у шары нет локального `$MFT`. Недоступный корень даёт
  явную ошибку с кодом выхода 2.

Оба режима теперь дают одинаковые значения `Size`, `On disk`, дат, атрибутов и счётчиков —
в том числе для резидентных файлов и корневого имени.

## 5. Индекс и дерево (`Core/ScanIndex.cs`, `Core/Node.cs`)

`ScanIndex` — плоские массивы (`long[]`, `int[]`, `string[]`, `uint[]`) вместо объекта на
каждый файл: 5 млн файлов занимают около 100 МБ вместо гигабайтов. Поля на объект:

| Поле | Смысл |
|---|---|
| `Parent` | индекс родителя, `-1` только у корня |
| `Name` | имя объекта (у корня — `Path.GetFileName`, например `AI`) |
| `Size` | логический размер файла / сумма логических размеров потомков |
| `Allocated` | сумма кластеров файла / потомков |
| `Attributes` | нормализованные атрибуты Windows |
| `Modified`, `Created` | локальное время из `$STANDARD_INFORMATION` или `WIN32_FIND_DATA` |

`BuildTree()` собирает иерархию один раз, затем снизу вверх агрегирует размеры и счётчики.
Благодаря этому:

- `Files` / `Folders` в строке папки — количество файлов/папок **во всём поддереве**, не только
 непосредственные потомки;
- колонка `Folders` в CSV — количество папок-потомков **без самой строки** (`SubtreeDirs - 1`);
- `SizeHuman` и `Percent` вычисляются уже после агрегации, относительно корня скана;
- атрибуты папки нормализуются: `0x10000000` → `0x10`, корень получает `0`;
- сортировка TUI не влияет на порядок записи CSV (он определяется обходом дерева).

## 6. Прогресс, журнал, завершение

- Фазы и счётчики обновляются по мере поступления записей; в MFT-режиме итоговые totals
  выставляются сразу после `BuildTree`, поэтому шапка не показывает нули после завершения
  разбора.
- `--log <файл>` пишет таймстемпы, фазы, периодические счётчики, примечания и итог. Сгенерированный
  PowerShell-скрипт удалённого скана тоже виден там же.
- Ctrl+C в TUI сбрасывает ANSI-атрибуты (`[0m`), курсор и режим мыши SGR и очищает экран.
  Код выхода — 130.
- `Environment.Exit` вызывается только после корректного закрытия файлов и transport-сессий.

## 7. Кодировки и форматы на границах

| Граница | Формат |
|---|---|
| CSV | UTF-8 **с BOM**, разделитель `,`, `\r\n`, заголовки и значения на английском |
| NDJSON (агент → хост) | UTF-8 **без BOM**, одна JSON-запись на строку, `\n`, `Flush()` пачками ~64 КБ (финальные записи — сразу) |
| WinRM-трафик | вывод агента пишется в файл на хосте, читается порциями до 2 МБ; PowerShell печатает `CH\t<base64>\t<pos>`, а C#-хост декодирует base64 и UTF-8 с состоянием (сохраняет имена на границе чанка) |
| Лог | UTF-8, текстовые строки с таймстемпом |

Подробности протокола — в [ARCHITECTURE.md](ARCHITECTURE.md), про CSV — в
[CSV-FORMAT.md](CSV-FORMAT.md).

## 8. Что остаётся за кадром

- Удалённый скан использует только обход каталогов; MFT-режим на удалённом хосте пока не
  включается.
- WinRM с Basic/незашифрованным HTTP требует доверенной сети (см. [REMOTE-SETUP.md](REMOTE-SETUP.md)).
- Подсчёт hardlink'ов — «по каталогам-владельцам»: один файл с несколькими `$FILE_NAME`
  увеличивает размер каждого каталога, в котором он числится. Это не «уникальные» байты тома.
