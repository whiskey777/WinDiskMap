# Архитектура и протокол удалённого скана

## Общая схема

```
                  ЛОКАЛЬНО                        |        УДАЛЁННЫЙ ХОСТ
                                                 |
 Program.cs                                      |
   ├─ локальный скан → ScanRunner ─┬─ MFT        |
   │                               └─ DirectoryWalk (Win32Find)
   │                                     │ IWalkSink
   │                                     ▼
   │                              ScanIndex / TreeBuilder → TUI / CSV
   │                                                     
   ├─ --agent-local → RemoteScanRunner → LocalAgentTransport ──► дочерний WinDiskMap --agent
   │                        │                                        (тот же путь, что ниже)
   │                        ▼ NDJSON (живьём)
   │                   TreeBuilder → TUI / CSV
   │
   └─ --remote host → RemoteScanRunner → PowerShellTransport ──WinRM──► WinDiskMap.exe --agent
                              │                                          ├─ MFT (если админ + NTFS)
                              ▼ NDJSON                                    └─ DirectoryWalk
                         TreeBuilder → TUI / CSV                              │
                                                                              ▼
                                                                      stdout → файл → чанки
```

Ключевой принцип: **один обход и один `TreeBuilder`** на все режимы. Агент не считает
агрегаты сам — он отдаёт плоские записи, хост строит дерево тем же кодом, что и при локальном
скане. Поэтому цифры локального и удалённого скана совпадают байт-в-байт.

## Роли одного exe

| Роль | Вызов | Что делает |
|---|---|---|
| Локальный сканер | `WinDiskMap <путь> [опции]` | MFT или обход, TUI/CSV/headless |
| Агент | `WinDiskMap --agent --path <локальный путь>` | сканирует LOCAL путь хоста, пишет NDJSON в stdout |
| Хост | `WinDiskMap --remote <host> --path <путь на хосте>` | поднимает WinRM, читает NDJSON, строит дерево |
| Отладочный хост | `WinDiskMap --agent-local --path <путь>` | как хост, но агент — локальный процесс |

`--remote` и `--agent-local` несовместимы с `--agent` (роль выбирается аргументами).

## Обход каталогов (`Core/DirectoryWalk.cs`, `Core/Win32Find.cs`)

- `FindFirstFileExW` с `FindExInfoBasic`: одно обращение даёт имя, атрибуты и размер;
  короткие имена DOS 8.3 не запрашиваются — длинные имена точны, лишних записей нет.
- Параллельные рабочие задачи кладут записи в общий `IWalkSink`; мутации дерева/id делает
  один поток-сборщик → результат детерминирован.
- Junction/symlink-каталоги не обходятся (защита от петель `Application Data`), но
  остаются в дереве с размером 0 и не попадают в счётчик папок.
- Сетевые пути: MFT недоступен, всегда обход; недоступный корень → явная ошибка.

## MFT (`Core/Mft/MftScanner.cs`)

- `$DATA` из extension-записи (`$ATTRIBUTE_LIST`) имеет приоритет над `$FILE_NAME`-фолбэком;
  у split-атрибута берётся максимум по экстентам.
- FN-ссылки расширения — дополнительные hardlink-пути базовой записи; дедуп по
  (родитель, имя); длинное имя из расширения вытесняет DOS-алиас.
- Reparse-флаг читается и из `$FILE_NAME`, и из `$STANDARD_INFORMATION`.
- Том с пустой меткой (нет корневого `$FILE_NAME`) обработан.
- `$MFT` включается в размер корня тома: это реально занятый файл, невидимый обходом.
- При провале MFT причина (тип, текст, `[stats: ...]` / `[lookup: ...]`) уходит в
  примечание и журнал, скан продолжается обходом.

## Протокол NDJSON

Одна строка = один JSON-объект. Кодировка UTF-8 **без BOM**, перевод строки `\n`.
Строки экранируются по JSON (`\"`, `\\`, `\uXXXX` для управляющих) — имена файлов могут
содержать что угодно, включая кавычки и переводы строк. Числа — десятичные, без разделителей.

| Запись | Поля | Смысл |
|---|---|---|
| `meta` | `mode` | текстовое название режима скана (для отчёта) |
| `phase` | `v` | фаза (`MFT`, `Обход каталогов`, ...) — живой прогресс |
| `note` | `v` | примечание (например, MFT недоступен → фолбэк) |
| `dir` | `id`, `parent`, `name`, `reparse` | каталог; `parent = -1` только у корня |
| `file` | `id`, `parent`, `name`, `size` | файл; `size` — логический размер |
| `end` | `files`, `dirs`, `bytes` | финальные счётчики |
| `error` | `v` | ошибка агента → хост прерывает скан |

Пример:

```json
{"t":"meta","mode":"Обход каталогов"}
{"t":"dir","id":0,"parent":-1,"reparse":false,"name":"C:\\Windows"}
{"t":"dir","id":1,"parent":0,"reparse":false,"name":"System32"}
{"t":"file","id":2,"parent":1,"size":4096,"name":"notepad.exe"}
{"t":"end","files":226958,"dirs":197558,"bytes":56146966797}
```

Порядок: корень первым, родитель всегда раньше ребёнка (BFS в `AgentRunner.EmitIndex`),
`id` нумеруются подряд с нуля. Хост подменяет имя корня на отображаемый путь
(`C:\Windows` → `\\host\C$\Windows`), остальные записи идут в `TreeBuilder` как есть.

Поток сбрасывается после каждой строки (`NdJsonWriter.Line()` → `Flush()`), поэтому TUI
пополняется во время скана, а не по его окончании.

## Транспорт WinRM (`Core/Remote/PowerShellTransport.cs`)

1. Генерация PowerShell-скрипта во временный `.ps1` (BOM UTF-8) — длинная командная
   строка с кавычками и Unicode не пережила бы `ProcessStartInfo.Arguments`.
2. Запуск `powershell.exe`/`pwsh` локально: `-NoProfile -NonInteractive -ExecutionPolicy
   Bypass -InputFormat None -OutputFormat Text -File <script>`, вывод декодируется как UTF-8.
3. Скрипт: две `New-PSSession` (одна под агента, вторая под чтение) → `Copy-Item -ToSession
   net48\WinDiskMap.exe` в `%TEMP%` хоста → `Invoke-Command -AsJob` запускает агента с
   перенаправлением stdout в файл → вторая сессия читает файл порциями до 256 КБ, lokalный
   локальный декодер UTF-8 с состоянием собирает строки и печатает их с префиксом `OUT\t` (ошибки —
   `ERR\t`). После завершения агента хвост файла вычитывается повторно, чтобы не потерять
   последние записи, затем файлы удаляются и обе сессии закрываются.
4. Хост-процесс (`WinDiskMap`) читает `OUT\t`-строки и вызывает `onLine` → `RemoteScanRunner`.

Почему файл, а не прямой stdout `Invoke-Command`: PowerShell десериализует вывод и
перекодирует его по кодовой странице консоли — Unicode-имена пострадали бы. Файл +
чтение байтами в UTF-8 сохраняет имена точно. Из-за же смены кодировки введены
`StandardOutputEncoding/StandardErrorEncoding = Encoding.UTF8` и защита парсинга чанка.

## Ошибки и восстановление

- `error` в потоке → `IOException` в `RemoteScanRunner` → `ScanSession.Error` → код выхода 2.
- Агент завершился без `end` → примечание «поток оборван».
- Неверный/`net48`-несовместимый агент, недоступная сессия → текст ошибки WinRM (при
  необходимости с `--log` виден полный сгенерированный скрипт).
- Ctrl+C в TUI восстанавливает `[0m`, курсор и отключает SGR-мышь.
